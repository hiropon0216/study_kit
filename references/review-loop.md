# レビューのループと章ごとのパイプライン

教材を書いたエージェントは、自分の書いたものの誤りや分かりにくさに気づきにくい。そこで、書いた担当とは別のエージェント（サブエージェント。以下「レビュー担当」）に読ませ、指摘がなくなるまで「直す → 見直す」を繰り返す。

superpowers の subagent-driven-development（作る係とレビュー係を分け、指摘は作った係が直し、上限つきの修正ループと記録ファイルで回す）にならった。

## 登場する担当

| 担当 | 何をするか |
|---|---|
| 作成担当 | このスキルを動かしているエージェント（メイン）。担当を立て、報告を受けて次の担当を立てる。**本文を読まず、直さない**（総合レビューの指摘だけは自分で直す） |
| リサーチ担当 | 章ごとに事実を集める（`references/workers/researcher.md`） |
| 章の担当 | 章を書き、その章のレビューの指摘を直す。パイプラインが終わるまで同じ担当が受け持つ（`references/workers/chapter-writer.md`） |
| レビュー担当 | 読んで指摘を書く。席ごとに新しく立てる（`references/reviewers/`） |
| 書き直し担当 | yomiyasu で地の文と解説文を書き直す（`references/workers/prose-rewriter.md`） |

## 章ごとのパイプライン

章ごとに次の順で進める。**章どうしは待ち合わせない。** 第1章が分かりやすさレビューに入っているときに、第3章がまだ書いている途中でもよい。作成担当は、担当から終わりの知らせが届くたびに、その章の次の段の担当を立てる。

```
リサーチ（researcher）
  → 書く（章の担当。--check でエラー0件・警告0件）
  → 妥当性レビュー r1（opus）
       指摘あり → 章の担当が直す（SendMessage）→ 再レビュー r2（sonnet。差分だけ）→ …（上限 r4）
  → yomiyasu で書き直す（1回だけ）→ 章の担当が意味の確認とリントの修正
  → 分かりやすさレビュー r1（sonnet）
       指摘あり → 章の担当が直す → 再レビュー r2 → …（上限 r4）
  → その章は完了
```

総合演習も、すべての章が「書く」を終えたら同じ形のパイプラインで進める（総合演習の担当が直す）。すべての章と総合演習が完了したら、`content.json` にまとめて総合レビューを1回行う。

なぜこうするか：以前は、全章のリサーチが終わるまで生成を待ち、全章の生成が終わるまでレビューを待ち、指摘は作成担当が1人で全章ぶん順に直していた。いちばん遅い章に毎段そろえるので時間がかかり、作成担当の文脈には全章の本文と指摘が積み上がっていた。章の担当に直させると、直す担当は自分の書いた章をすでに読んでいるので読み直しが要らず、章どうしが同時に進む。

## 状態の記録

作成担当は、章ごとにいまどの段にいるかを `<出力先>/work/review-ledger.md` の先頭の表に書き、段が進むたびに直す。会話が要約されたあとは、この表から再開する。

```
| 範囲 | 段 | 担当のID | メモ |
|---|---|---|---|
| ch1 | 分かりやすさ r2 待ち | a1b2c3（章の担当） | |
| ch2 | 妥当性 r1 待ち | d4e5f6 | |
| ch3 | 書く | g7h8i9 | リサーチで「〇〇は断定しない」 |
| final | 未着手 | | ch3 の書き終わり待ち |
```

担当のIDは、章の担当に SendMessage で直しを頼むために控える。

## レビューの席

| 席 | いつ | 見ること | テンプレート | モデル |
|---|---|---|---|---|
| ゴールの整合 | フェーズ1（章立てをユーザーに出す前） | 章立てでゴールに届くか、論点がズレていないか | `references/reviewers/goal-reviewer.md` | opus |
| 妥当性 | 章のパイプライン | 事実がファクトシートと合うか、正解が1つに決まるか、ゴールに沿っているか | `references/reviewers/validity-reviewer.md` | opus |
| 分かりやすさ | 章のパイプライン | 想定する学習者が読んでつまずかないか、AIっぽい日本語が残っていないか | `references/reviewers/clarity-reviewer.md` | sonnet |
| 再レビュー | 各ループの2回目以降 | 指摘が直ったか、直した箇所が新しく壊れていないか | `references/reviewers/re-reviewer.md` | sonnet |
| 総合 | フェーズ5 | 教材を通して読んで、ゴールを達成できるか | `references/reviewers/final-reviewer.md` | opus |

- サブエージェントを呼ぶときは、モデルを必ず指定する。指定しないと、いまのセッションのモデルがそのまま使われる
- 席ごとに新しいレビュー担当を立てる。前の席のレビュー担当に続けて頼まない（前の判断に引きずられるため）。直す側（章の担当）は同じ担当を使い続ける
- r1 で重大・要修正が0件だった章は、再レビューをしない。その席はそこで完了にする
- ゴールの整合レビューは r1 だけにする。直した章立ては、次にユーザーが承認のときに読むため、再レビューを挟まない

## レビュー担当への渡し方

- 渡すものはファイルのパスにする。教材やファクトシートの中身をプロンプトに貼りつけない
- **教材全体を渡さない。** レビューの範囲に要るものだけを切り出して渡す

  | 席 | 渡すもの | 作り方 |
  |---|---|---|
  | 妥当性・分かりやすさ | 章の切り出し（その章の本文・問題・事実・前の章で説明済みの固有名詞） | `assemble.py <出力先> --slice N -o <出力先>/work/slices/chN.json`（総合演習は `--slice final`） |
  | 再レビュー | 直す前と直した後の差分（変わった項目・問題・事実だけ） | `diff_content.py <出力先>/work/history/chN_<席>_r<回>.json <出力先>/work/chN.json -o <差分>` |
  | 総合 | 教材の骨組み（見出し・要点・固有名詞の初出・問題文と正解） | `slice_content.py <出力先>/content.json --all -d <出力先>/work/slices` が作る `outline.json` |

  章のファイルを直したら、次の席に渡す前に切り出し直す
- 渡すものは、テンプレートに書いたものだけにする。作成担当がそれまでに考えたことや経緯は渡さない
- 指摘はレビュー担当が `<出力先>/work/reviews/<席>-<範囲>-r<回>.md` に書く。作成担当への返事は「重大 N 件・要修正 N 件・軽微 N 件」と書いたファイルのパスだけにさせる。作成担当は指摘ファイルを読まず、そのパスを章の担当に送る
- **先回りして指摘を封じない。** 「〇〇は指摘しなくてよい」「軽微として扱って」のような指示をプロンプトに書かない。誤った指摘だと思っても、出させてから判断する
- レビュー担当は、さらにサブエージェントを呼ばない（テンプレートに書いてある）

## 指摘の重さ

| 重さ | 例 | 扱い |
|---|---|---|
| 重大 | 事実の誤り、正解が1つに決まらない、ファクトシートにない記述、ゴールと関係のない節、前提を説明していない固有名詞 | ループで直す |
| 要修正 | 想定する学習者がつまずく説明、説明の飛躍、AIっぽい言い回し、図と本文の食い違い、論点がゴールから少しズレている | ループで直す |
| 軽微 | 言い回しの好み、あると良い補足 | 記録だけしてループに入れない。総合レビューに一覧を渡す |

## 回数の上限

- 1つの席で、初回のレビュー（r1）のあとの「修正 → 再レビュー」は**3回まで**（r2〜r4）
- r4 の再レビューでも指摘が残ったら、それ以上回さない。章の担当に、残った指摘を1件ずつ判断させ、判断と理由を修正メモに書かせる。作成担当はその判断を記録に写す
  - レビュー担当の誤り、または意見が分かれる → 残す。判断の理由を記録する
  - 指摘は正しいが、ゴールの達成に響かない → 残す。「正しいが後回し」と記録する
  - 指摘は正しく、ゴールの達成に響く → いちばん小さな直し方を決めて直し、記録する
- 上限の前に判断でループを打ち切らない。打ち切りは、指摘を封じるのと同じことになる

## 記録ファイル（ledger）

`<出力先>/work/review-ledger.md` に、先頭の状態の表と、ループの経過と判断をすべて残す。

```
# レビュー記録 — 教材ID: k8s-practical
（状態の表）

goal r1: 重大 1・要修正 2・軽微 1（work/reviews/goal-all-r1.md）→ 直してユーザーに提示
validity ch1 r1: 重大 2・要修正 3（work/reviews/validity-ch1-r1.md）
validity ch1 r2: 4件直った・1件残り（q-ch1-ex-04 の選択肢2が条件次第で正解）
validity ch1 r3: 残り1件
validity ch1 r4: 残り1件（上限）
validity ch1: 判断：q-ch1-ex-04 は選択肢2を差し替え — 条件を問題文に足すより確実 — 誤りなら問題が易しくなるだけ
軽微（後回し）：ch2-s1 i3 の比喩をもっと身近にできる
```

- 判断は `判断：<何を決めたか> — <なぜ> — <誤りだったときの影響>` の形で書く
- 再開するときは、状態の表と記録の最後の行から続ける。「完了」と書いた席はやり直さない

## 渡すときの報告

フェーズ6でユーザーに教材を渡すとき、記録ファイルの「判断：」の行をすべて、決めた順に「レビューで判断したこと」として添える。担当たちがユーザーの代わりに決めたことは、ここでしかユーザーに伝わらない。

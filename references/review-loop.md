# レビューのループ

教材を作ったエージェント（以下「作成担当」）は、自分の書いたものの誤りや分かりにくさに気づきにくい。そこで、作成担当とは別のエージェント（サブエージェント。以下「レビュー担当」）に読ませ、指摘がなくなるまで「直す → 見直す」を繰り返す。

superpowers の subagent-driven-development（作る係とレビュー係を分け、上限つきの修正ループと記録ファイルで回す）にならった。

## 全体像

```
作成担当が作る
  → レビュー担当（新しいサブエージェント）が読み、指摘をファイルに書く
  → 作成担当が指摘を仕分ける（重大・要修正はループへ、軽微は記録だけ）
  → 作成担当が直す
  → 再レビュー担当が「指摘が直ったか」と「直した箇所が新しく壊れていないか」だけを見る
  → 残りがあれば次の回へ（上限まで）
  → 上限に達したら、残った指摘を作成担当が1件ずつ判断し、判断を記録する
```

## レビューの席

| 席 | いつ | 見ること | テンプレート | モデル |
|---|---|---|---|---|
| ゴールの整合 | フェーズ1（章立てをユーザーに出す前） | 章立てでゴールに届くか、論点がズレていないか | `references/reviewers/goal-reviewer.md` | opus |
| 妥当性 | フェーズ4-1 | 事実がファクトシートと合うか、正解が1つに決まるか、ゴールに沿っているか | `references/reviewers/validity-reviewer.md` | opus |
| 分かりやすさ | フェーズ4-5 | 想定する学習者が読んでつまずかないか、AIっぽい日本語が残っていないか | `references/reviewers/clarity-reviewer.md` | sonnet |
| 再レビュー | 各ループの2回目以降 | 指摘が直ったか、直した箇所が新しく壊れていないか | `references/reviewers/re-reviewer.md` | sonnet |
| 総合 | フェーズ4-6 | 教材を通して読んで、ゴールを達成できるか | `references/reviewers/final-reviewer.md` | opus |

- サブエージェントを呼ぶときは、モデルを必ず指定する。指定しないと、いまのセッションのモデルがそのまま使われる
- 席ごとに新しいサブエージェントを立てる。前の席のサブエージェントに続けて頼まない（前の判断に引きずられるため）

## レビュー担当への渡し方

- 渡すものはファイルのパスにする。教材JSONやファクトシートの中身をプロンプトに貼りつけない（作成担当のコンテキストを圧迫するため）
- 渡すものは、テンプレートに書いたものだけにする。作成担当がそれまでに考えたことや経緯は渡さない
- 指摘はレビュー担当が `<出力先>/work/reviews/<席>-<範囲>-r<回>.md` に書く。作成担当への返事は「重大 N 件・要修正 N 件・軽微 N 件」と書いたファイルのパスだけにさせる
- 章が多いときは、章ごとにレビュー担当を分けて同時に走らせてよい（レビューは読むだけなので衝突しない）。直すのは作成担当1人で、順番に行う
- **先回りして指摘を封じない**。「〇〇は指摘しなくてよい」「軽微として扱って」のような指示をプロンプトに書かない。誤った指摘だと思っても、出させてから判断する
- レビュー担当は、さらにサブエージェントを呼ばない（テンプレートに書いてある）

## 指摘の重さ

| 重さ | 例 | 扱い |
|---|---|---|
| 重大 | 事実の誤り、正解が1つに決まらない、ファクトシートにない記述、ゴールと関係のない節、前提を説明していない固有名詞 | ループで直す |
| 要修正 | 想定する学習者がつまずく説明、説明の飛躍、AIっぽい言い回し、図と本文の食い違い、論点がゴールから少しズレている | ループで直す |
| 軽微 | 言い回しの好み、あると良い補足 | 記録だけしてループに入れない。総合レビューに一覧を渡す |

## 回数の上限

- 1つの席で、初回のレビュー（r1）のあとの「修正 → 再レビュー」は**3回まで**（r2〜r4）
- r4 の再レビューでも指摘が残ったら、それ以上回さない。作成担当が残った指摘を1件ずつ判断する
  - レビュー担当の誤り、または意見が分かれる → 残す。判断の理由を記録する
  - 指摘は正しいが、ゴールの達成に響かない → 残す。「正しいが後回し」と記録する
  - 指摘は正しく、ゴールの達成に響く → いちばん小さな直し方を決めて直し、記録する
- 上限の前に判断でループを打ち切らない。打ち切りは、指摘を封じるのと同じことになる

## 記録ファイル（ledger）

`<出力先>/work/review-ledger.md` に、ループの経過と判断をすべて残す。会話が長くなって要約されても、このファイルを見ればどこまで進んだか分かる。

```
# レビュー記録 — 教材ID: k8s-practical
goal r1: 重大 1・要修正 2・軽微 1（work/reviews/goal-all-r1.md）
goal r2: 3件とも直った
goal: 完了
validity ch1 r1: 重大 2・要修正 3（work/reviews/validity-ch1-r1.md）
validity ch1 r2: 4件直った・1件残り（q-ch1-ex-04 の選択肢2が条件次第で正解）
validity ch1 r3: 残り1件
validity ch1 r4: 残り1件（上限）
validity ch1: 判断：q-ch1-ex-04 は選択肢2を差し替え — 条件を問題文に足すより確実 — 誤りなら問題が易しくなるだけ
軽微（後回し）：ch2-s1 i3 の比喩をもっと身近にできる
```

- 判断は `判断：<何を決めたか> — <なぜ> — <誤りだったときの影響>` の形で書く
- 再開するときは、記録ファイルの最後の行から続ける。「完了」と書いた席はやり直さない

## 渡すときの報告

フェーズ5でユーザーに教材を渡すとき、記録ファイルの「判断：」の行をすべて、決めた順に「レビューで判断したこと」として添える。作成担当がユーザーの代わりに決めたことは、ここでしかユーザーに伝わらない。

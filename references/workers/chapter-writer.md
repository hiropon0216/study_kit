# 章の担当（フェーズ3〜4）

章ごとに新しいサブエージェントを立てる。その章のリサーチが終わったら、ほかの章を待たずに立てる。章どうしは別のファイル（`work/chN.json`）に書くので衝突しない。

章の担当は、その章を書き終えたあとも、章のパイプライン（`references/review-loop.md`）が終わるまで同じ担当が受け持つ。レビューの指摘を直すときは、作成担当が新しいエージェントを立てず、SendMessage でこの担当に指摘ファイルのパスを送る。この担当は自分の書いた章と根拠の事実をすでに読んでいるので、読み直さずに直せる。

```
Agent:
  subagent_type: general-purpose
  model: opus
  description: "第[N]章を書く"
  prompt: |
    あなたは [トピック] の教材を書く担当です。第[N]章「[章タイトル]」を書いてください。
    書き終えたあとも、この章のレビューの指摘を直す役を続けて受け持ちます。

    最初に [GEN_SPEC] を読んでください。これがあなたの要件です。章立て・固有名詞の割り当て・
    書き方・問題の作り方・出力の形は、すべてこのファイルに従います。そこに書かれた
    「必ず読むもの」を読んでから書き始めます。

    - 事実の基準：[出力先]/work/facts/ch[N].md（この章のリサーチ担当が集めた事実）
    - リサーチで分かった注意：[FACT_NOTES]
    - 書くのは第[N]章だけです。ほかの章のファイルは書きません
    - 第[N]章より前の章で前提を説明済みの固有名詞：[EXPLAINED_BEFORE]
    - あなたはさらにサブエージェントを呼びません
    - 出力：[出力先]/work/ch[N].json。書き終えたら
      `py [SKILL_DIR]/scripts/assemble.py [出力先] --check [N]` でエラー0件・警告0件にする

    最後の返事は、次の表と短い報告だけにしてください。
    | 節ID | 項目数 | すぐ確認の数 | variants の数 |
    - 章末演習の数、追加した事実（extraFacts）のID、仕様の表にない固有名詞を出したならその語、
      残した警告とその理由
```

## 埋めるもの

- `[GEN_SPEC]`：`<出力先>/work/gen-spec.md`
- `[FACT_NOTES]`：その章のリサーチ担当の報告の「見つからなかったこと」「断定してはいけないこと」（なければ「なし」）
- `[EXPLAINED_BEFORE]`：生成の共通仕様の「固有名詞の割り当て」のうち、前の章に置く語（第1章なら「なし」）

## モデル

本文と問題の質は、この担当で決まる。そのため、ほかの担当より能力の高いモデル（opus）を使う。レビューで直すより、最初によく書くほうが全体の手間が少ない。

## 指摘を直してもらうとき（SendMessage で送る文）

作成担当は、直し始める前に `work/chN.json` を `work/history/chN_<席>_r<回>.json` にコピーしておく（再レビューに渡す差分のため）。

### レビューの指摘を直す（妥当性・分かりやすさ）

```
[席] レビューの指摘です：[FINDINGS_FILE]
重大・要修正の行をすべて直してください。軽微は直さなくてよいです。
- 直すのは [出力先]/work/ch[N].json だけ。指摘の場所の前後だけを直し、ほかの文は変えない
- 指摘が誤りだと思うものは直さず、理由を修正メモに書く
- ファクトシートにない記述を直すときは、facts/ch[N].md の事実で書き直すか、削除する。
  追加で調べてよいのは、ゴールに欠かせない記述だけ（検索3回まで）。裏が取れたら extraFacts に入れ、
  取れなければ削除する。どちらにしたかを修正メモに書く
- 直したら `assemble.py [出力先] --check [N]` でエラー0件・警告0件にする
- 修正メモ：[FIX_NOTE]（指摘の # ごとに、どう直したか／直さなかった理由）
最後の返事は「直した N 件・直さなかった N 件 — [FIX_NOTE]」の1行だけにしてください。
```

### 書き直し（yomiyasu）のあとに意味を確かめる

```
yomiyasu の書き直しを ch[N].json に書き戻しました。書き直しで事実の意味が変わっていないかを確かめ、
リントの警告を直してください。
1. `py [YOMIYASU_DIR]/scripts/yomiyasu_diff.py [出力先]/work/prose/prose_ch[N].md [出力先]/work/prose/revised_ch[N].md --stance=説明`
   の出力と前後の文を見比べ、意味が変わったところ（「〜の場合がある」の断定化、条件・数値・主語・否定の脱落）を
   書き直す前の意味に戻す
2. `py [SKILL_DIR]/scripts/extract_prose.py [出力先]/work/ch[N].json -o [出力先]/work/prose_final/prose_ch[N].md` で
   抜き出し直し、`py [YOMIYASU_DIR]/scripts/yomiyasu_lint.py` にかけた結果を
   [出力先]/work/prose_final/lint_ch[N].txt に保存する。警告は直す。直さないもの（段落をまたいだ
   「同一文末が3回以上連続」など）は理由をメモに書く
3. `assemble.py [出力先] --check [N]` でエラー0件・警告0件にする
- メモ：[出力先]/work/reviews/prose-ch[N]-check.md（戻した箇所・残した警告と理由）
最後の返事は「意味を戻した N 件・残した警告 N 件 — メモのパス」の1行だけにしてください。
```

- 章の担当が使えなくなったとき（エラーで止まった、会話が切れた）だけ、新しいサブエージェントを立てて同じ文を渡す。そのときは「最初に [GEN_SPEC] の書き方のルールと、ch[N].json の指摘の場所の前後を読む」を足す

# 総合演習の担当（フェーズ3〜4）

すべての章の担当が書き終え、`--check` を通したら立てる（章のレビューが終わるのを待たない）。総合演習は節の数×10問以上と数が多いので、ゴールごとに分けて2〜3人で同時に書いてよい。総合演習のパイプライン（妥当性レビュー → 書き直し → 分かりやすさレビュー）でも、指摘はこの担当に SendMessage で直させる。

```
Agent:
  subagent_type: general-purpose
  model: opus
  description: "総合演習 [担当範囲] を書く"
  prompt: |
    あなたは [トピック] の教材の総合演習を書く担当です。[担当範囲（例：G1・G2 に直結する問題を40問）] を書いてください。
    書き終えたあとも、この問題のレビューの指摘を直す役を続けて受け持ちます。

    ## 読むもの
    - 生成の共通仕様：[GEN_SPEC]（学習者・ゴール・問題のルール）
    - 教材の骨組み：[OUTLINE]（全章の節・項目の見出し、要点、すでにある問題の問題文と正解。
      本文は入っていない。問題を作るのに本文の細部が要るときだけ、[出力先]/work/chN.json を
      節IDで Grep し、その節の前後だけを読む。全体を読まない）
    - 問題の作り方：[SKILL_DIR]/references/question-guide.md の「総合演習」
    - 事実の基準：[出力先]/work/facts/（章ごとのファクトシート。要る事実を Grep で引く）

    ## 決まり
    - 複数の章の知識を組み合わせないと解けない問題にし、ゴールの「使う場面」を問う
    - すでにある問題（骨組みに載っている）と同じことを問わない
    - ID は [ID_RANGE]（例：q-final-01〜q-final-40）。`refs` には2章分以上を入れる
    - あなたはさらにサブエージェントを呼ばない
    - 出力：[出力先]/work/final_[番号].json に {"questions": [...]} の形で書く

    最後の返事は、問題数・形式ごとの数・ゴールごとの数の表だけにしてください。
```

- `[OUTLINE]`：`py <SKILL_DIR>/scripts/assemble.py <出力先> --slice outline -o <出力先>/work/slices/outline.json` で作る
- 総合演習の検査は、`assemble.py <出力先> --draft` で仮の教材を作り、`validate.py <出力先>/work/content_draft.json` にかける

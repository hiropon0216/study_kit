# フェーズ4：レビュー観点

順番は 妥当性レビュー → 表現の改修 → 意味の差分チェック → リント → 分かりやすさレビュー → 総合レビュー → 最終チェック。入れ替えない。

妥当性・分かりやすさ・総合の3つは、作成担当とは別のエージェント（サブエージェント）が読み、指摘がなくなるまで直す。進め方（席・指摘の重さ・回数の上限・記録ファイル）は `references/review-loop.md`、各席に渡すプロンプトは `references/reviewers/` にある。

## 1. 妥当性レビュー（ループ。`references/reviewers/validity-reviewer.md`）

### 1-1. 事実

教科書の各文・各問題の正解・各解説について、次を確かめる。

- [ ] ファクトシートのどの事実が根拠か特定できる
- [ ] 根拠の事実と内容が食い違っていない（数値・条件・範囲・バージョン）
- [ ] 事実の強さが変わっていない（「〜の場合がある」を「〜する」と言い切っていない、その逆もない）
- [ ] 図（SVG・`sk-cells` など）の中の値や名前が、本文・ファクトシートと食い違っていない
- [ ] 節の `sources` に、本文が使った事実がそろっている
- [ ] まぎらわしい項目の組（`confusables`）の `note` が、両方の項目の本文と食い違っていない

### 1-2. 問題

- [ ] 正解が1つに決まる。ほかの選択肢が条件次第で正解にならない
- [ ] 穴埋めの許容表記に漏れがない
- [ ] 並べ替えの正しい順が1通りに決まる
- [ ] ○×（truefalse）の文が、言葉尻ではなく事実で正誤が決まる
- [ ] すぐ確認が、直前の項目の本文だけを読めば解ける（本文に答えの手がかりがある）
- [ ] 選択式の問題文だけで、答えが1つに決まる（選択肢を見なくても答えを思い浮かべられる）
- [ ] 言い換え問題（`variants`）が、元の問題と同じ知識を問い、正解が1つに決まる

### 1-3. ゴールとの整合（論点のズレ）

基準は `work/goal-brief.md`（フェーズ0で学習者と確かめたゴールの要約）。

- [ ] 各節・各項目が、どのゴールに役立つか言える
- [ ] 説明や例が、ゴールの「使う場面」に沿っている。ゴールより一般論・概論に寄っていない
- [ ] ゴールの要約の「これだと外れ」に当たる説明・問題になっていない
- [ ] 章末演習・総合演習の問題が、ゴールの場面を問うている

### 1-4. 固有名詞

- [ ] 固有名詞（`references/proper-nouns.md` の対象）がすべて、初出の項目で `sk-premise` か本文によって前提から説明されている。4つの観点のうち「何か」と「この教材との関係」が欠けていない
- [ ] 問題文・選択肢・解説・コードに、前提を説明していない固有名詞が出ていない

### 指摘の直し方

説明のない固有名詞を見つけたら、`sk-premise` を初出の節に足す。必要な事実はファクトシートにない記述と同じ手順（下記）で集める。

ファクトシートにない記述が見つかったら、追加リサーチを1回行う。

- S か A の出典が見つかった → ファクトシートに事実を追加し、`sources` に加える
- 見つからない → 記述を削除する。問題なら差し替える
- どちらの場合も `factCheckLog` に記録する

## 2. 表現の改修

- [ ] yomiyasu の SKILL.md を読み込み、ドメイン `tech` で適用した
- [ ] 対象は `extract_prose.py` が抜き出した地の文と解説文だけ
- [ ] `<!-- prose: ID -->` の目印を消していない・順番を変えていない
- [ ] `sk-premise` の段落を短くしすぎていない。冒頭の `**何か：**` などの見出しを消していない（前提の説明は情報密度より分かりやすさを優先する）
- [ ] `apply_prose.py` がエラーなしで書き戻せた

## 3. 意味の差分チェック

`yomiyasu_diff.py --stance=説明` の出力と、改修前後の文を見比べる。

- [ ] 「〜の場合がある」「〜ことが多い」が断定になっていない
- [ ] 条件（「〜のとき」「〜なら」）が落ちていない
- [ ] 数値・単位・バージョン・コマンド名・オプション名が変わっていない
- [ ] 主語や対象が入れ替わっていない（Deployment が作る／ReplicaSet が作る、など）
- [ ] 否定が肯定になっていない、その逆もない
- [ ] 固有名詞の前提の説明（何か／誰が作ったか／なぜ必要か／この教材との関係）が削られていない

意味が変わっていたら、改修前の意味に戻す。

## 4. リント

- [ ] `yomiyasu_lint.py` の出力を `work/lint.txt` に保存した（分かりやすさレビューに渡す）
- [ ] 警告を確認した。残した警告は理由を記録した（段落をまたいだ文末の連続、専門用語の前後の空白など）

## 5. 分かりやすさレビュー（ループ。`references/reviewers/clarity-reviewer.md`）

レビュー担当は、ゴールの要約から作った**想定する学習者**として読む。

### 5-1. 学習者としてのつまずき

- [ ] 説明なしに出てくる語がない（学習者の「いまできること」に入っていない語は説明する）
- [ ] 前の項目で説明していないことを前提にしていない
- [ ] 結論だけを並べず、「なぜそうなるか」が書いてある
- [ ] 説明の途中の段が飛んでいない
- [ ] 図を見て、何を読み取ればよいか分かる
- [ ] 問題文が何を聞いているか一読で分かる。解説を読んで「なぜその答えか」が分かる

### 5-2. 読みやすさ（認知負荷）

学習者の頭の作業を、理解に関係ないことに使わせないための観点（Mayer, R. E. (2020). *Multimedia Learning* (3rd ed.). Cambridge University Press のマルチメディア学習の原則のうち、文字と図の教材に当てはまるもの）。

- [ ] **近接**：図の説明が図から離れていない。図の中の要素の名前は図の中に書き、凡例や本文を行き来しないと読めない図にしていない
- [ ] **一貫性**：理解に関係のない雑談・豆知識・飾りの図を入れていない（面白くても、本筋から注意をそらす話は削る）
- [ ] **冗長**：図に書いたことを、地の文でそのまま読み上げていない。地の文は図の読み方や「なぜ」を足す
- [ ] **合図**：その項目で大事な語・図の中の大事な部分が、`<strong>` や `sk-fill-mark` で示されている（示しすぎていない）
- [ ] **分割**：1つの項目で説明することが1つになっている。長くなった項目は分けている
- [ ] **具体 → 抽象**：原理を説明する項目が、具体的な場面から始まっている（`references/textbook-components.md`）

### 5-3. AIっぽい日本語

yomiyasu で直したあとに残ったものを拾う。基準は yomiyasu の SKILL.md。

- [ ] 無生物主語の文（「この設定が〜を可能にする」）が、誰が何をするかの文になっている
- [ ] 比喩的な動詞（「〜を支える」「〜を担う」）が、具体的な動作になっている
- [ ] 不要なカッコ書きの補足、過剰な太字・箇条書きがない
- [ ] 「〜ではなく、〜だ」の否定と対比の型を多用していない
- [ ] 文単体で、誰が何をどうしたかが分かる

### 指摘の直し方

直した文は、事実の意味（条件・数値・強さ・主語）を変えない。再レビュー担当が、直した箇所の意味が変わっていないかを確かめる。

## 6. 総合レビュー（`references/reviewers/final-reviewer.md`）

- [ ] 各ゴールに、学ぶ場所（節）と確かめる問題がある
- [ ] 後ろの章が、前の章で説明していない語や考え方を前提にしていない
- [ ] 教材全体として、ゴールの要約の「これだと外れ」に寄っていない
- [ ] レビュー記録の「判断：」と後回しにした軽微な指摘を見直した

## 7. 最終チェック

- [ ] 分かりやすさレビューと総合レビューで直したあと、`yomiyasu_lint.py` をもう一度かけ、新しい警告がない
- [ ] `validate.py` のエラーが0件
- [ ] 警告を確認し、残したものは理由を記録した

## 報告の形式

各席のレビュー担当は、指摘を `work/reviews/` のファイルに表で書く（形は `references/reviewers/` の各テンプレート）。作成担当は、ループの経過と判断を `work/review-ledger.md` に記録する（`references/review-loop.md`）。

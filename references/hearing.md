# フェーズ0：ヒアリング項目

ヒアリングの目的は、章立ての前にゴールをはっきりさせること。ゴールがあいまいなまま章立てに進むと、教材の論点が学習者の欲しいものから少しずつズレる。3点を聞いて終わりにせず、学習者が教材を終えたあとの**具体的な場面**まで聞き取る。

## 必須の3点

| 項目 | 聞き方の例 | 回答例 |
|---|---|---|
| トピック | 何を学びたいですか | Kubernetes |
| 目的 | 資格合格・実務で使える・教養として理解する、のどれに近いですか | 実務で使えるようになりたい |
| 現在の知識レベル | 関連する分野で、いま何ができますか | Docker は日常的に使うが、Kubernetes は触ったことがない |

- 目的は `meta.purpose` の「資格」「実務」「教養」のどれかに対応させる
- 知識レベルは「〜を知っている」より「〜ができる」で聞く。章立ての出発点（前提にしてよい知識）を決めるのに使う

## ゴールを具体にする質問

3点がそろったら、次の観点を1つずつ聞く。一度に並べて聞かない。学習者の言葉をそのまま記録する（言い換えると意図が落ちる）。

| 観点 | 聞き方の例 | 回答例 | 使い道 |
|---|---|---|---|
| 使う場面 | 教材を終えたあと、どんな場面で、何をしていたいですか。直近で困った場面があれば教えてください | 社内の検証クラスタで、Pod が起動しないときに自分で原因を調べたい | ゴール（「〜できる」）の素材。総合演習の場面 |
| 外れの例 | 教材がどうなっていたら「欲しかったのはこれじゃない」と感じますか | 概念の説明ばかりで、コマンドを打つ場面がない | 「扱わないもの」と、レビューで論点ズレを判定する基準 |
| すでに知っている／試したこと | 公式ドキュメントや本など、すでに試したものはありますか。何が合いませんでしたか | 公式チュートリアルは手順を追えたが、なぜそうするのか分からなかった | 説明の深さと書き方の方針 |
| 優先度 | 1つだけ確実にできるようになるとしたら、どれですか | 障害の切り分け | 重要度 A の節を決める |

- 答えがあいまいなときは、こちらの推測を1つ示して直してもらう（「〇〇のために△△したい、ということで合っていますか」）。選択肢を並べると学習者の答えが選択肢に引っぱられるので、まず自由に話してもらう
- 「おまかせ」と言われた観点は、こちらで決めた内容を一行で伝える。伝えずに決めない

## 資格試験の場合に追加で聞くこと

| 項目 | 使い道 |
|---|---|
| 試験名（と版・年度） | 試験シラバスを信頼度 S の出典にする |
| 問題数 | 模擬試験モードの `meta.exam.questionCount` |
| 制限時間（分） | 模擬試験モードの `meta.exam.minutes` |
| 合格ライン（%）※分かれば | 模擬試験モードの `meta.exam.passingRate` |

## 聞かないこと

- 期限・1日の学習時間（学習エンジンの設計に使わないため）
- 自信の度合い（「不明」ボタンで代わりにする）

## ゴールの要約と確認

聞き取りが済んだら、次の形で要約を返し、違っている点を直してもらう。学習者が言ったことと、こちらの推測を分けて書く。

```
## 学習のゴール（要約）
- トピック／目的／いまできること：…
- 教材を終えたあとの場面：…（学習者の言葉）
- これだと外れ：…（学習者の言葉）
- いちばん優先すること：…
- こちらの推測（違っていたら直してください）：…
```

- 学習者が「合っている」と言うまでフェーズ1に進まない
- 確定した要約を `<出力先>/work/goal-brief.md` に保存する。フェーズ1以降のレビュー担当（サブエージェント）は、この文書をゴールの基準として読む

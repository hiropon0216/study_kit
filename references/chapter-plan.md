# フェーズ1：章立ての書式

## 1. ゴール

「〜できる」の形で数個（目安2〜5個）書く。学習者が教材を終えたときに、具体的な場面で何ができるかを書く。

- 良い例：Pod が起動しないとき、kubectl で原因を切り分けられる
- 悪い例：Pod を理解する（できたかどうか確かめられない）
- フェーズ0で確かめたゴールの要約（`work/goal-brief.md`）の「使う場面」から作る。学習者の言葉からかけ離れた言い換えにしない
- 「いちばん優先すること」に当たるゴールを G1 にする

ゴールは `meta.goals` にそのまま入り、総合演習の問題はこのゴールに直結する場面から作る。

## 2. 章立て表

ゴールに必要な知識を逆算し、前提関係の順（前の節を知らないと読めない節は後ろ）に並べる。

| 章 | 節 | 重要度 | 項目（＝すぐ確認で問うこと） | 問題数 | 対応するゴール | 想定時間 |
|---|---|---|---|---|---|---|
| 第1章 Kubernetes の基本オブジェクト | 1-1 Pod | B | ①Pod は最小のデプロイ単位 ②同じ Pod のコンテナは localhost で通信できる ③Pod の定義はマニフェストに書く ④Pod は直接作らない | 6問 | G1 | 15分 |
| | 1-2 Deployment と ReplicaSet | A | ①3段の管理 ②ロールアウトが始まる条件 ③rollout status／undo ④例題：replicas の変更 | 8問 | G1, G2 | 20分 |

- 節は「項目（説明＋すぐ確認）」の並びでできる。1節に項目3〜6個（説明2〜5個＋必要なら例題1個）。重要度 A の盛りだくさんな節は8個まで
- 項目は「すぐ確認で問える1つの事柄」の単位で区切る。表に項目を書いておくと、承認のときに粒度を確かめてもらえる
- 想定時間は「読みながらすぐ確認を解く」時間で1節あたり15分前後を目安にする（重要度 A の節は問題が多いぶん長くてよい）

### 重要度と問題数

すぐ確認の数は、**学習の目的（ゴール）に対する重要度に比例させる**。目的に近い節ほど問題を増やし、何度も思い出させる。重要度は節ごとに章立ての段階で決め、承認をもらう。

| 重要度 | どんな節か | すぐ確認の数（1節あたり） |
|---|---|---|
| A | ゴールに直結する中心の節。実務・試験でそのまま使う知識や手順。内容が盛りだくさんな節 | 項目数 × 2 以上（重要な項目は2〜4問） |
| B | ゴールを支える標準の節 | 項目数 × 1.5 以上（重要な項目に2問） |
| C | 前提・補助・背景の節 | 項目数 × 1（各項目1問） |

- 1つの項目に問題を複数付けるときは、同じことを言い換えて数を増やさない。その項目の別の事実や、別の角度（用語・値・判断・手順）から問う（`references/question-guide.md`）
- 1項目の問題は4問まで。それより多く問いたい内容は、項目を分ける
- 迷ったら、その節を飛ばしたときにゴールが達成できなくなるか（なるなら A）で決める
- 教材JSONの節の `importance` に入れる。`validate.py` が、重要度に対して問題が少ない節を警告する
- 各章の最後に章末演習（10問以上）、教材の最後に総合演習（節の数×10問以上）が付くことも書き添える
- 対応するゴールがない節は、本当に必要かを見直す

## 3. 固有名詞の一覧

章立てに出てくる固有名詞を、初めて出てくる節の順に列挙する（対象にする語は `references/proper-nouns.md`）。各語は初出の節で前提から説明する。

| 語 | 種類 | 初出の節 |
|---|---|---|
| Kubernetes（K8s） | ソフトウェア | 1-1 |
| Docker | ソフトウェア | 1-1 |
| YAML | ファイル形式 | 1-1 |
| kubectl | コマンド | 1-1 |

迷った語も一覧に入れる。学習者が「これは知っているので不要」と言った語も、短い説明は残す。

## 4. 今回扱わないもの

表とは別に、関連するが今回は扱わない内容を列挙する。承認時に抜けを指摘してもらうため。

- 例：Helm、Operator、マルチクラスタ運用、クラスタの構築手順

- ゴールの要約の「これだと外れ」に当たる内容は、ここに書くか、章立てで扱い方を変える

## 5. ゴールの整合レビュー（ユーザーに出す前）

1〜4 を `<出力先>/work/chapter-plan.md` に保存し、別のエージェント（サブエージェント）に、この章立てでゴールに届くかを確かめさせる。プロンプトは `references/reviewers/goal-reviewer.md`、進め方は `references/review-loop.md`。

- 重大・要修正の指摘がなくなるまで「直す → 再レビュー」を繰り返す（上限は r4 まで）
- 上限に達して残った指摘は、どう判断したかを承認のときにユーザーへ伝える

## 6. 承認

- 章立て表と一緒に、ゴールの整合レビューで直したことを2〜3行で添える
- 「この章立てで進めてよいですか。足りない内容や不要な内容、説明してほしい固有名詞があれば教えてください」と聞く
- 修正指示があれば表を直して再提示する
- ユーザーが明示的に OK を出すまでフェーズ2に進まない
